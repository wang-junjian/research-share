# 文档两跳发布管线

一份本地 HTML → 一个能在微信里转发的链接 → 一张站点上的卡片。这是两件不同的事，本技能把它们连成一条可复跑的链。

```
① 资料库（第 1 跳）                                   ② 研究成果站（第 2 跳）
   import_html.py   上传 → 「页面」节点                    POST /api/items
   publish_page.py  发布 → workbuddy.link/p/<nodeId>   → 列表卡片 + /item/<id> + /og/<id>.png
        ↑ 任何人不登录可看，带目录、表格、交互                ↑ 专属分享封面 + 真实摘要，微信卡片好看
        └──────────── node_id 当幂等键 ────────────────────┘
```

**两跳各解决一个特定问题，缺一不可**：

- 资料库解决「别人不登录也能读到原文」，但它的分享卡片是通用模板（`og:image` 是 HTML 文件图标、`og:description` 是固定文案「WorkBuddy - 可人机协作的在线 Page」）——发到微信里很敷衍。
- 研究成果站解决「分享出去好看」，但它只存卡片元数据，正文要么跳资料库、要么把静态 HTML 存进自己库里。

所以给用户交付时，**要发的是站点详情页 `/item/<id>`，不是 workbuddy.link 链接**。

## 一条命令跑完

> 下面所有命令都假定当前目录是技能目录：`cd ~/.workbuddy/skills/share-doc-publish`。

> **`--title` 优先填文档自己的标题**（h1，无 h1 用 `<title>`），别一上来就自拟；`--summary` 不要现写现填。先按「第二关」判定原标题能否直接用，再按「第三关」一次生成多组摘要候选、用 `shortlist` 择优，把定稿那一组传进来。

```bash
python3 scripts/publish.py all <本地文件.html> \
  --title "文档自己的标题（优先用 h1 原文；≤300 字）" \
  --summary "实质概览（≤400 字，目标 200–360 字，卡片和详情页都用它）" \
  --date 2026-11-03
```

跑完输出三段：资料库公开链接、编辑链接、站点详情页与封面图，外加验收结果。

先看会做什么、不落任何东西：

```bash
python3 scripts/publish.py all <file> --title … --summary … --dry-run
```

`--dry-run` 不上传、不写入——第 1 跳一旦执行就会在资料库里真建一个页面。

## 标题与摘要：字数、专业度与多候选择优

这两个字段是卡片上唯一需要人定稿的文字，也是微信分享卡唯一读得到的文字（`og:title` / `og:description`）。**标题优先用文档自己的标题，别只生成一版然后反复改**：一次给出几组不同角度的候选，以专业技术编辑的身份逐组评审，挑最适合的那一版。完整规范、审查清单与择优示例见 [`references/editorial-standards.md`](references/editorial-standards.md)。

### 第一关 字数：硬上限脚本拦，目标区间编辑把关

站点接口对这两个字段有硬上限，超一个字就 400。**坑在于它是在第 1 跳已经把页面传上去之后才拒的**（2026-11-03 真实踩过：summary 403 字，资料库里白建了一个页面）。所以校验现在**挪到了上传前**——超硬上限时命令直接退出，资料库连页面都不会建。

| 字段 | 硬上限（脚本阻断） | 生成目标区间（编辑审查） | 计数口径 |
|---|---|---|---|
| `--title` | **300 字** | **20–40 字** | UTF-16 码元：中文/西文各算 1、emoji 算 2，与服务端 JS `s.length` 完全同口径 |
| `--summary` | **400 字** | **200–360 字** | 同上 |

目标区间不是「建议」而是生成要求：短于 20 / 200 字说明没把成果讲清楚，长于 40 / 360 字通常是在灌水，越界的候选在择优时直接淘汰，不用改字硬救。**唯一例外：标题沿用文档自己的标题时，20–40 区间豁免**（见第二关）——原文不该为了凑字数被改写；传 `--doc-title` 后脚本不再报警，只在 `review.info` 留痕。300 字硬上限、套话与格式检查**不豁免**。`publish.py meta` 会把这两项连同其它可机检项一起报进 `review.warnings`——**它只提示、不阻断发布**（阻断只认硬上限），事实是否站得住、读起来是否想点开，仍按第三关逐项判。

**展示端的三个截断点**（`lib/render.js`，决定了文字该怎么写）：

| 去处 | 口径 | 对写作的约束 |
|---|---|---|
| 详情页 `og:description`（微信卡片） | `truncate(summary, 80)` | **只有前 80 字进微信**，且标题/描述各最多两行。第一句必须是自带结论的完整钩子，不能是「本文介绍了……」 |
| 分享海报 `data-summary` | `truncate(summary, 220)` | 前 220 字要能独立成篇 |
| 列表卡片 `col-deck`、纯文字分享 `data-overview` | 完整 summary | 详情页全文展示，别只写个引子 |

超限时报错长这样，别硬撞：

```
error: 标题/摘要不合规，未上传（资料库没有被建页面）：summary 403 字，超上限 3 字（上限 400）
```

改字之前先数字数、顺带看审查提示，不联网、不落库；标题用原文时把 `--doc-title` 一起传：

```bash
python3 scripts/publish.py meta --title "…" --summary "…" --doc-title "文档自己的标题"
```

`meta` 返回 `title_len` / `summary_len` 与 `title_left` / `summary_left`（还能写多少字，负数即超出量），`ok=false` 时 `problems` 里直接写「超了 N 字」；`meta.title_is_doc_title` 与 `review.title_is_doc_title` 标明标题是否就是文档原标题，`review.info` 说明豁免了什么；`review` 段给出目标区间、禁用套话、格式、首句长度等可机检提示，以及 `review.og_hook`（微信卡片实际会显示的前 80 字，审的时候直接读它）。**别用 `len()` 自己数**：emoji 这类字符服务端算 2、Python `len()` 算 1，本地看着够、线上必 400。

### 第二关 生成：标题先取原文，摘要写成技术编辑会签发的样子

先读正文再动笔——从 h1、章节标题、表头、结论段里取**事实**（做了什么、怎么做的、数据是多少、边界在哪），不要凭文件名猜。

#### 标题：优先使用文档自己的标题

**默认定稿就是文档自己的标题，不要另拟**。卡片标题和读者点开后看到的第一行文字一致，才算对得上；自拟的「卡片句式」再漂亮，也是在替作者改题目。

| 顺序 | 取哪个 | 说明 |
|---|---|---|
| 1 | **h1** | 正文主标题，读者在文档里看到的那个；多个 h1 取第一个 |
| 2 | `<title>` | 无 h1 时用它。脚本兜底取全文；若带站点名 / 日期后缀（如 `… · 2026-10`），显式 `--title` 给主标题部分，并在对比表写明去掉了什么 |
| 3 | 文件名 | 前两者都没有才用，且必须在对比表里写明「原标题缺失」 |

`python3 scripts/precheck.py <file>` 会同时打印 `<title>` 与 h1（注意它没有 `scan` 子命令，文件路径就是第一个位置参数），`publish.py` 的兜底链与这个顺序一致。h1 里的 `<br>` 只当视觉换行、不产生空格：实测 `<h1>免费部署 Web 应用的云服务<br>全景研究</h1>` 抠出来是 `免费部署 Web 应用的云服务全景研究`（19 字）。

**先判原标题能不能用**，四条全过就**直接定稿**，不必为标题造候选（摘要仍按第三关出多版）：

| # | 判据 | 不通过的例子 |
|---|---|---|
| 1 | 是实质标题，不是文件名 / 占位符 | `index`、`CAPTURE_PIPELINE_GUIDE`、`未命名文档` |
| 2 | 不超 **300 字**硬上限（UTF-16 码元） | 把整段摘要塞进 `<title>` |
| 3 | 无营销腔、emoji、HTML 标签、换行等格式杂质 | `深度解析：彻底搞定文档发布🎉` |
| 4 | 有可辨识的对象，不是空泛套话 | `关于一些研究与实践分享` |

**只有原标题不合格才自拟**，且必须在候选对比表里写明「原标题是什么、为什么不适用」。自拟才用「研究对象 + 具体动作/结论」的陈述句，20–40 字，吸引力来自**具体**而非形容词：

- 好：`两跳发布管线：把本地 HTML 变成可分享的研究成果卡片`
- 差：`关于文档发布流程的一些研究与实践分享`（无对象、无结论、无信息量）

沿用原标题时 **20–40 字目标区间豁免**（上面那个 19 字 h1 就是合格标题，别硬凑成 20 字）；300 字硬上限、套话与格式检查照旧。

**摘要**：200–360 字，四段式，一段一句、顺序固定：

1. **钩子（前 80 字内，必进微信卡片）**：这份成果解决什么问题 / 得出什么结论，自带实体与结论；
2. **做法**：关键技术路径或方法，带得上专名就带（如 `X-Agent-Token`、CSP sandbox、UTF-16 码元）；
3. **证据**：可复核的数字、实测结论或验证方式（条数、字节数、状态码、耗时对比）；
4. **边界与适用**：什么情况下不适用、有哪些已知代价，给读者判断要不要点开。

一段只干一件事；**不许编造**——每个数字、专名、结论都要能在正文里指出出处；不复述标题，不写成「本文分为五章」的目录。禁用清单（套话、营销腔、空洞形容词、第一人称、未展开的缩写、emoji、换行、markdown 标记、省略号收尾）见 references 第四节。

### 第三关 多候选择优：一次给几版，挑最适合的发

**不要只生成一版然后反复改**。标题按第二关先定：**原标题可用 → 三组候选共用这个标题，只比摘要**；原标题不可用 → 才连标题一起出改写候选，并在对比表写明理由。

一次生成 **3 组**候选（`title` + `summary` 成对），摘要的**角度要真的不同**，否则择优只是在三句同义改写里挑：

| 候选 | 切入角度 | 首句重心 |
|---|---|---|
| A 结论导向 | 突出可复核的结果与数字 | 「实测 … / 得到 …」 |
| B 问题导向 | 突出解决了什么具体麻烦 | 「… 会让 …；做法是 …」 |
| C 方法导向 | 突出架构 / 机制上的关键一笔 | 「用 … 把 … 收口」 |

三组都要先满足第二关（字数、四段式、禁用清单），别拿一个明显不合格的版本凑数。

**一次机检全部候选**：写成带顶层 `doc_title` 的 JSON 对象（也收纯数组 / `{"candidates": [...]}`），把文档原标题写进去，跑：

```bash
python3 scripts/publish.py shortlist /tmp/candidates.json          # 也支持管道：cat … | … shortlist
python3 scripts/publish.py shortlist /tmp/candidates.json --doc-title "文档自己的标题"   # 覆盖 JSON 里的值
```

```json
{
  "doc_title": "免费部署 Web 应用的云服务全景研究",
  "candidates": [
    {"id": "A", "title": "免费部署 Web 应用的云服务全景研究", "summary": "…"},
    {"id": "B", "title": "免费部署 Web 应用的云服务全景研究", "summary": "…"}
  ]
}
```

它按「硬上限 → **原文标题版优先** → warnings 数 → 目标区间贴合度」排序，输出每组的字数、`title_is_doc_title`、`og_hook` 前 80 字、顶层 `doc_title_candidates` 与 `recommended`。**没传 `doc_title` 时排序与旧版完全一致**；`recommended` 仍只覆盖形式，不是定稿。传了却一组都没标成原文版，说明候选池里漏放了原标题，或该批确实在走「原标题不适用」分支——要在对比表写明（references 第七节是「原标题未提供」分支的完整例子：脚本推荐 A、C 被机检淘汰，编辑按读者场景选了 B）。

**再以技术编辑视角逐组判**，7 项清单：

| # | 审查项 | 由谁判 |
|---|---|---|
| 1 | 字数落在目标区间（沿用原标题时 20–40 豁免），且没踩硬上限 | 脚本 |
| 2 | 无禁用套话、无营销腔、无格式杂质 | 脚本 |
| 3 | 前 80 字自成完整钩子，微信卡片能读懂 | 人工（脚本另查首句 ≤80 字） |
| 4 | 标题优先沿用文档原标题；若改写，需具体有对象且写明改写理由 | 人工 |
| 5 | 每个术语、数字、结论都能在正文里找到出处，**没有编造** | 人工 |
| 6 | 摘要四段齐备，不与标题复述、不写成目录 | 人工 |
| 7 | 读完后读者能判断「这跟我有关吗 / 我要不要点开」 | 人工 |

脚本只判形式（1、2 与第 3 项的首句长度），第 4 项只标注 `title_is_doc_title`、判不了该不该改写。**`review.pass=true` 不等于审查通过**——3～7 的内容判定必须逐组给出结论。

**择优规则**：

1. **先淘汰**：机检不过、或 #5 事实可溯不过的候选直接出局，不要因为「文笔好」留着。
2. **优先原文标题版**：`doc_title_candidates` 里合格的候选先选。若最终改写了标题，必须在对比表写明「原标题是什么 + 第二关哪条判据不过」；原标题已合格却另拟一版更「漂亮」的，判 #4 不通过。
3. **按场景选**：这批成果的读者最关心什么，就选对应角度的那一版（结论 / 问题 / 方法），不选看起来最华丽的。
4. **允许取长补短**：A 的摘要首句最强、B 的证据段更扎实，可以组合成一版；组合后**必须重跑一次 `meta`**——拼接最容易把 summary 顶过 400 或把首句撑过 80 字。标题若被换成非原文，按第 2 条写理由。
5. **写下选择理由**：`候选 / 角度 / 是否原文标题 / 机检 / 7 项判定 / 选它的理由` 记进交付回复，别只丢一个结果。
6. **不必走满任何轮次**。只有**整批候选全不合格**时才再生成一批，最多 3 批；第 3 批仍全不合格，取问题最少的一版并明确标注「未通过编辑审查」及剩余问题，交用户决定改字还是照发——**不静默降级，也不擅自发一个自己都判不合格的版本**。
7. 定稿后跑一次 `meta` 确认硬上限，再执行发布（两跳非事务，见下）。

### 两条老规矩

- **`title` 优先用文档自己的标题**（h1 → `<title>` → 文件名），别习惯性另拟；要改写就在候选对比表里写明原标题为什么不适用。
- `summary` 别照抄资料库的 og 描述——那是固定文案「WorkBuddy - 可人机协作的在线 Page」，要按正文重写成实质概览（`meta` 会认出这句话）。

不传 `--title` 时脚本按同一顺序兜底，报告里 `meta.title_source` 写明实际来源（`doc_h1` / `doc_title_tag` / `filename` / `arg`），`meta.doc_title` 给出原文标题、`meta.title_is_doc_title` 标明是否沿用。兜底值也参与字数校验；超长时报错会提示用 `--title` 显式给短的。**兜底不算「生成」，不能跳过上面三关**——它只是让漏传时不至于发出一个叫 `index` 的卡片。最好总是显式写 `--title`：原标题可用时直接填它，并给 `meta` / `shortlist` 传 `--doc-title`（或候选 JSON 顶层 `doc_title`），让机检认得出原文标题版。

## 先体检，再决定形态

```bash
python3 scripts/precheck.py <file>
```

`verdict` 三种取值决定下一步：

| verdict | 含义 | 怎么办 |
|---|---|---|
| `ok` | 干净，无 WAF 红线 | 两种形态都能发 |
| `needs_sanitize` | 含 `<script>` / 内联事件 / `javascript:` | 链接型可直接发；要走文档型先 `sanitize.py` |
| `blocked` | 不存在 / 非 HTML / 超限 / 取不到标题 | 停下来问用户 |

**只有 `.html` / `.htm` 能走这条路。** 资料库只在 HTML 上生成「页面」节点，而 `publish_page` 只对页面节点有效。markdown / pdf / docx 得先转成单文件 HTML。

### 两种形态怎么选

| | 链接型（默认） | 文档型 `--mode doc` |
|---|---|---|
| 正文在哪 | 资料库，跳 `workbuddy.link` | 本站数据库，`/item/<id>/doc` 直出 |
| 脚本交互 | **保留**（目录滚动高亮、tab 都能用） | 必须剥掉（WAF 拦 `<script`） |
| 改内容 | 资料库改一次即可，站点不用重发 | **不可改**，只能删除重发 |
| 域名 | 两个（资料库 + 站点） | 一个（全在站点域名下） |
| 适用 | 默认选这个，站内既有内容全是这个形态 | 要求「链接都在自己域名下」或资料库链接不想暴露 |

文档型的隔离由托管路由的 `Content-Security-Policy: sandbox allow-scripts` 独力承担（ADR-0004）：脚本就算被写进去也摸不到本站会话。所以 `sanitize` 剥脚本是为了过 WAF，不是安全所必需——但两者效果一致。

## 脚本

| 脚本 | 作用 |
|---|---|
| `scripts/precheck.py` | 体检：体积、标题、WAF 红线、编辑器污染、外链 |
| `scripts/sanitize.py` | 清成静态 HTML：剥 script/iframe/on*/javascript:/编辑器属性 |
| `scripts/publish.py` | 主流程：`scan` / `meta` / `shortlist` / `library` / `site` / `all` / `verify` |
| `references/editorial-standards.md` | 标题与摘要的技术编辑标准、原标题优先规则、审查清单、多候选择优示例 |
| `references/pipeline-facts.md` | 接口与展示端的实测证据底稿 |

`publish.py` 的子命令可以单独跑，用来接续或排障：

```bash
python3 scripts/publish.py meta --title … --summary … [--doc-title …]          # 数字数 + 可机检的编辑审查（不联网、不落库）
python3 scripts/publish.py shortlist <candidates.json> [--doc-title …]         # 多组候选一次机检 + 择优排序（也收 stdin）
python3 scripts/publish.py library <file> [--space-id S] [--node-block-id ID]   # 只做第 1 跳
python3 scripts/publish.py site --title … --summary … --url … --source-key …    # 只做第 2 跳
python3 scripts/publish.py verify <item_id>                                     # 只验收 / 巡检
```

`--node-block-id` 是对已有页面重导入（更新内容），不传就是新建。重跑整条链时**必须带上它**，否则资料库里会堆出重复页面。

## 验收标准（不看返回码）

```bash
python3 scripts/publish.py verify <item_id>
```

| 检查项 | 判据 | 为什么不能只看 200 |
|---|---|---|
| `detail_200` | `/item/<id>` 返回 200 | — |
| `og_200` | `/og/<id>.png` 返回 200 且 **> 2000 字节**（正常约 5900） | 演示模式也返回 200，只是内容全是示例数据 |
| `listed_on_home` | 首页 HTML 里能找到条目标题 | 60 秒内存缓存：接口写完即时失效，绕库直改则会滞后 |
| `source_link_live` | 公开页 `<title>` 不是通用壳页 | **取消发布后 workbuddy.link 仍返回 200**，只是换成 5957 字节的 `<title>WorkBuddy</title>` 空壳 |
| `doc_route_200` / `doc_csp_sandbox` | 仅文档型：`/item/<id>/doc` 200 且响应头含 `sandbox` | 托管原文与隔离头是这个形态的全部价值 |

站点总条数用 `/api/health` 的 `count` 对账：新建 +1，幂等重投不变。

## 会咬人的地方

1. **`Authorization: Bearer` 会被边缘代理吃掉**，线上 401 `missing_token`。必须用 `X-Agent-Token`。本地直连看不出来，只在线上暴露。
2. **`doc_html` 里出现 `<script` / `onclick=` / `javascript:` → 平台 WAF 直接返回 403 的 HTML 拦截页**，不是本站 JSON，请求根本到不了应用。看到 `waf_suspect` 就是这个。
3. **新建返回 201，幂等更新返回 200**。只认 200 会把成功判成失败（本人踩过，卡片其实已经建好了）。
4. **资料库导出的副本被编辑器回写过**：同一份文档原件 118KB、导出件 231KB，剥掉属性后分别是 102,474 与 141,881 字符。要发布就用**原件**；手上有导出件时先看 `precheck.py` 报的 `pollution`。
5. **Agent API 的返回里没有 `kind` 字段**。判断一个条目是不是文档型，只能探 `/item/<id>/doc`：200 是，404 是链接型。
6. **标题 ≤300、摘要 ≤400，且两跳不是事务**：第 1 跳一跑完资料库就有页面了，第 2 跳再因超长 400，那个页面白建。校验已前置到上传前（见上文「标题与摘要」），真撞上了就用 `--node-block-id <已有 node_id>` 带幂等键重跑，别重新新建。
7. **同一份文档的两种形态不能互转**：已存在的 `source_key` 若是链接型，重投文档型只会更新标元，`kind` 保持不变（db/06 的既定行为）。要换形态就换 `source_key`（如加 `:doc` 后缀）。
8. **别拿封面图字节数判断「是不是同一张图」**：`/og/<id>.png` 全是 5915 B——它是「研究笔记横格纸」抽象图，不含任何文字字形，只靠一条朱红批注线的位置（内容哈希决定）区分。字节数相同是设计如此，不是渲染失败或占位骨架。

## 收尾

发布完成后：

- 站点条目一旦删除就**没有回收站**，`/item/<id>` 随即 404、旧卡片链接失效。要改内容优先 `PATCH` 改标题/摘要，别删。
- 资料库页面用 `page/unpublish_page.py --node-id <id>` 可取消发布（公开链接随即变成壳页）。
- 把「源文件路径 / node_id / 站点 id / 公开链接」记进项目日志，下次重发才找得到幂等键。

更多细节与实测证据见 `references/pipeline-facts.md`。
