# 标题与摘要：技术编辑标准与审查清单

这份文件是 `SKILL.md`「标题与摘要」一节的展开底稿，写给**要签发这两个字段的技术编辑**，也写给按本技能跑发布的智能体。所有展示端数字都来自 `lib/render.js` 与 `README.md`，改版式时要跟着改这里。

---

## 一、为什么标准长这样：四个读者，四种截法

同一份 `summary` 会被四处消费，截法各不相同。写的时候按**最短的那个**先写，再往后补。

| 消费方 | 代码位置 | 口径 | 对写作的约束 |
|---|---|---|---|
| 微信 / 分享卡 `og:description` | `renderDetail`: `truncate(it.summary, 80)` | 前 **80** 个 UTF-16 码元，超出补 `…` | 前 80 字必须自带完整结论 |
| 分享海报 `data-summary` | `renderDetail`: `truncate(it.summary, 220)` | 前 **220** 字 | 前 220 字要能独立成篇 |
| 首页卡片 `col-deck` / 头条 `feat-deck` | `renderIndex` | 完整 summary，行数由 CSS 控制 | 首句决定要不要点 |
| 详情页 `.detail-summary` / `data-overview` | `renderDetail` | 完整 summary | 是全文概览，不是引子 |

`truncate` 用 JS `s.length`（UTF-16 码元），与接口限长的计数口径一致。`publish.py meta` 的 `review.og_hook` 会把这 80 字原样打出来，审的时候**直接读它**，不要脑补；`review.first_sentence_len` 给出首句长度，须 ≤80 字，否则卡片会停在半句。`og_hook_truncated_mid_sentence=true` 只说明卡片末尾停在第二句中间——**只要首句完整就属正常**，不必为此重写。

微信卡片的高度由微信控制（README「微信分享的三条现实约束」）：标题最多两行、描述最多两行，超了直接截断。所以「把关键信息放在第三句」等于没写。

## 二、标题：优先使用文档自己的标题

**默认定稿 = 文档自己的标题**。卡片标题与读者点开后看到的第一行文字一致，才算对得上；自拟的「卡片句式」再漂亮，本质是在替作者改题目。顺序是「先取原文 → 判能否用 → 不能才自拟」，不是「先想一句漂亮的」。

### 取哪个

| 顺序 | 来源 | 口径 |
|---|---|---|
| 1 | **h1** | 正文主标题，多个 h1 取第一个 |
| 2 | `<title>` | 无 h1 时用。`precheck.py` 与 `publish.py` 兜底都取全文；带站点名 / 日期后缀（如 `… · 2026-10`）时显式 `--title` 给主标题部分，并在对比表写明去掉了什么 |
| 3 | 文件名 | 前两者都无才用，且必须写明「原标题缺失」 |

`python3 scripts/precheck.py <file>` 同时打印 `<title>` 与 h1（`precheck.py` 没有 `scan` 子命令，路径就是第一个位置参数；多写一个词会被当成文件名，报「文件不存在」）。`publish.py` 报告里的 `meta.title_source` 会写 `doc_h1` / `doc_title_tag` / `filename` / `arg`。**h1 里的 `<br>` 是排版换行、不是词间空格**：实测 `<h1>免费部署 Web 应用的云服务<br>全景研究</h1>` 抠出 `免费部署 Web 应用的云服务全景研究`（19 字）。来源不同的两串标题差一两个空格时，脚本用 `same_title()` 折叠空白后比较，不会把原文版误判成改写版。

### 原标题能不能直接用（四条全过就定稿）

| # | 判据 | 不通过的例子 |
|---|---|---|
| 1 | 是实质标题，不是文件名 / 占位符 | `index`、`CAPTURE_PIPELINE_GUIDE`、`未命名文档` |
| 2 | 不超 **300 字**硬上限（UTF-16 码元） | 把整段摘要塞进 `<title>` |
| 3 | 无营销腔、emoji、HTML 标签、换行等格式杂质 | `深度解析：彻底搞定文档发布🎉` |
| 4 | 有可辨识的对象，不是空泛套话 | `关于一些研究与实践分享` |

四条全过 → **标题直接定稿，不进候选池**，摘要仍按第六节出多版择优。此时 **20–40 字目标区间豁免**：`免费部署 Web 应用的云服务全景研究` 只有 19 字，仍是合格标题，别硬凑到 20 字。`meta` / `shortlist` 传了 `--doc-title`（或候选 JSON 顶层 `doc_title`）后，`review.title_is_doc_title=true`，区间越界只写进 `review.info`、不进 warnings；**300 字硬上限、套话、格式检查不豁免**。

### 原标题不合格才自拟

自拟才用 `研究对象 + 具体动作/结论`（必要时 `：+ 方法 / 结果`），**20–40 字**，且必须在候选对比表里写明「原标题是什么、上面哪条判据不过」。吸引力来自**具体**，不来自形容词：

| 判定 | 例 | 为什么 |
|---|---|---|
| 通过 | `两跳发布管线：把本地 HTML 变成可分享的研究成果卡片` | 对象（本地 HTML → 分享卡片）、动作（两跳）、产物可核对 |
| 通过 | `X-Agent-Token 替代 Bearer：边缘代理吞头问题的实测与回归` | 有专名、有具体问题、有验证方式 |
| 不通过 | `关于文档发布流程的一些研究与实践分享` | 无对象、无结论，「一些 / 研究 / 分享」全是零信息词 |
| 不通过 | `深度解析：彻底搞定文档发布🎉` | 营销腔 + 绝对化 + emoji |

## 三、摘要：四段式，200–360 字

四段各一句（最多两句），顺序固定，总计 **200–360 字**。大致按 80 / 80 / 100 / 60 字分配，别让第一段吃掉一半篇幅。

| 段 | 干什么 | 字数 | 通过判据 |
|---|---|---|---|
| ① 钩子 | 解决什么问题 / 得出什么结论 | ≤80 | **自带实体与结论**，脱离标题也读得懂；这一句就是微信卡片 |
| ② 做法 | 关键技术路径、方法、组件 | 60–90 | 出现具体专名或机制，不是「采用了一系列优化」 |
| ③ 证据 | 可复核的数字、实测结论、验证方式 | 70–110 | 至少一处能被命令 / 日志 / 状态码复跑的数字或事实 |
| ④ 边界 | 什么情况不适用、代价、已知限制 | 40–70 | 给出读者判断「要不要点开」的依据 |

**四条硬规矩**：

- **不许编造**。每个数字、专名、结论都要能在正文里指出出处。正文没写就不要写进摘要——宁可少一句证据，也不要凭常识补。
- **不复述标题**。第一句若是标题的换词重说，等于浪费了最金贵的前 80 字。
- **不写成目录**。「本文分为五章，分别介绍……」是目录，不是概览。
- **一段只干一件事**。把「做法 + 证据 + 边界」揉成一句长句，读者在卡片上只会看到半句。

**首句自检**：把 `review.og_hook` 单独拿出来读一遍。若它像「本文介绍了 X 的相关内容」，或读完后不知道结论是什么，判不通过。

## 四、禁用清单（脚本会报，编辑也要判）

`publish.py meta` 的 `review_meta` 用正则扫下面这些；命中进 `warnings`，**不阻断发布**，但该候选应在择优时淘汰或改写。注意 `--doc-title` 只豁免**标题的字数区间**，套话、营销腔、格式杂质照旧会报——原标题本身就带「深度解析」时，要么在对比表写明「原文如此」并保留，要么按第二节判它不合格后改写。

| 类别 | 具体词 / 模式 | 问题 |
|---|---|---|
| 指代开场 | `本文介绍了`、`本篇阐述`、`这份文档…` | 前 80 字全花在指代上 |
| 自媒体套话 | `深度解析`、`全面梳理`、`一文读懂`、`干货`、`保姆级`、`重磅`、`独家` | 制造分量，不传递信息 |
| 绝对化 | `革命性`、`颠覆性`、`业界领先`、`彻底解决`、`完美`、`最佳实践` | 无法证实，技术读者会直接不信 |
| 填充连接 | `众所周知`、`显而易见`、`毋庸置疑`、`值得一提的是` | 删掉不丢信息 |
| 推给正文 | `等等`、`限于篇幅`、`不再赘述`、`详见全文` | 卡片上等于没写 |
| 第一人称 | `我们在…`、`笔者`、`本人认为` | 卡片上应直接陈述事实 |
| 格式杂质 | 换行、markdown 标记、HTML 标签、emoji、全角空格、省略号 / 破折号收尾 | 卡片与海报渲染会出问题 |

脚本的 HTML 标签检测只认常见标签名，技术摘要里的 `<node_id>` / `<id>` 这类占位符不会误报。**未展开的缩写**（第一次出现就写 `RLS`、`WAF` 而不给全称）脚本判不了，归人工项 #5。

**资料库固定文案**：`WorkBuddy - 可人机协作的在线 Page`——照抄会被单独报出来，必须按正文重写。

## 五、技术编辑审查清单（7 项，逐候选判通过 / 不通过）

审查时把自己当成要在刊物上签发这段文字的人：**读者只有卡片上那两行，凭什么点开**。

| # | 项 | 判据 | 谁判 |
|---|---|---|---|
| 1 | 字数 | title 20–40（沿用原标题时豁免）、summary 200–360，且未踩 300 / 400 硬上限 | 脚本 |
| 2 | 禁用与格式 | 第四节清单零命中 | 脚本 |
| 3 | 微信钩子 | `review.og_hook` 脱离标题仍读得懂、自带结论、是一句完整的话 | 人工（脚本另查首句 ≤80 字且有句末标点） |
| 4 | 原标题优先 | 优先沿用文档原标题；若改写，写明第二节哪条判据不过，且自拟标题具体、有对象 | 人工 |
| 5 | 事实可溯 | 每个数字、专名、结论在正文里能指出处；**没有编造** | 人工 |
| 6 | 结构完整 | 四段齐备；首句不复述标题；不是目录式罗列 | 人工 |
| 7 | 读者决策 | 读完能判断「跟我有关吗 / 要不要点开」；边界段给了取舍依据 | 人工 |

脚本只判形式：1、2，以及第 3 项的首句长度与句末标点；第 4 项它只**标注** `title_is_doc_title`，判不了「该不该改写」。**跑完 `meta` 看到 `review.pass=true` 不等于审查通过**——3～7 的内容判定必须由人（或按技能执行的智能体）**逐组逐项**给出结论，这是最容易偷懒的一步。多组候选一起判时用 `shortlist`，见第六节。

## 六、多候选择优：一次给几版，挑最适合的

**主流程不是「生成一版 → 审 → 不合格重写 → 再审」的串行返工**，而是「一次铺开几版 → 横向比 → 选最适合的」。理由很实际：串行返工每一轮都带着上一版的措辞惯性，改到第三轮往往只剩同义反复；换角度重起一版，才真能比出高下。

**标题先按第二节定，再谈候选**：原标题四条判据全过 → 三组候选共用这个标题，只比摘要；原标题不合格 → 才连标题一起出改写候选，并在对比表写明理由。别默认「每版都要换个标题」，那等于把原标题优先规则架空。

**一次生成 3 组候选**（`title` + `summary` 成对），摘要角度必须真的不同：

| 候选 | 切入角度 | 首句重心 | 适合什么读者 |
|---|---|---|---|
| A 结论导向 | 可复核的结果与数字 | 「实测 … / 得到 …」 | 想先知道值不值得做 |
| B 问题导向 | 解决了什么具体麻烦 | 「… 会让 …；做法是 …」 | 正踩在这个坑里 |
| C 方法导向 | 架构 / 机制上的关键一笔 | 「用 … 把 … 收口」 | 想照着复现 |

3 是默认、不是硬规定：内容简单给 2 组也够，角度分不开就别硬凑第 3 组。**三组都要先满足第二、三节的写作标准**，不要故意放一个明显不合格的版本来衬托其它两组。（第七节的 C 不是凑数的坏稿：它是认真写的方法导向版本，只因首句过长被机检筛掉，正好用来演示淘汰判据。）

### 一次机检全部候选

写成 JSON 数组，或带顶层 `doc_title` 的包装对象（推荐，能标出原文标题版）：

```json
{
  "doc_title": "免费部署 Web 应用的云服务全景研究",
  "candidates": [
    {"id": "A", "title": "免费部署 Web 应用的云服务全景研究", "summary": "…"},
    {"id": "B", "title": "免费部署 Web 应用的云服务全景研究", "summary": "…"},
    {"id": "C", "title": "免费部署 Web 应用的云服务全景研究", "summary": "…"}
  ]
}
```

```bash
python3 scripts/publish.py shortlist /tmp/candidates.json
python3 scripts/publish.py shortlist /tmp/candidates.json --doc-title "文档自己的标题"   # 覆盖 JSON 里的值
# 或从 stdin：cat candidates.json | python3 scripts/publish.py shortlist
```

输出按「硬上限 → **原文标题版优先** → warnings 数 → 目标区间贴合度」排序（没传 `doc_title` 时这一项对所有组相同，排序与旧版一致）。每组给 `title_len` / `summary_len`、`title_is_doc_title`、`ok`（能不能发）、`review_pass`（机检过不过）、`failed_checks`、`warnings`、`og_hook`、`first_sentence_len`；顶层给 `doc_title`、`doc_title_candidates` 与 `recommended`。整批无合格候选时返回 `recommended=null`、退出码 1。

**`recommended` 只是形式上的最优，不是定稿**。「原文标题版优先」是排序项，但其余仍是「离区间中点的距离」这类形式量，读不出「这批读者最关心什么」；把脚本推荐当最终选择，等于把编辑判断外包给几个正则。反过来，`doc_title_candidates` 为空时要警觉：要么候选池漏放了原标题，要么这批确实在走「原标题不适用」分支，理由要写进对比表。

### 择优五步

1. **先淘汰**：机检不过（`eligible=false`）、或 #5 事实可溯不过的候选直接出局，别因为「文笔好」留着。淘汰要写下原因并指到字段和位置（「C 首句 206 字，微信卡片会停在半句」），不写「不够专业」。
2. **优先原文标题版**：`doc_title_candidates` 里合格的候选先选。若最终改写了标题，必须在对比表写明「原标题是什么 + 第二节哪条判据不过」；原标题已合格却另拟一版更漂亮的，判 #4 不通过。
3. **按场景选**：在剩下的候选里挑**角度最贴这批读者**的一版，而不是最华丽的。判据是 #7：读者读完能不能决定要不要点开。
4. **允许取长补短**：A 的摘要首句最强、B 的证据段更扎实，可以组合成一版；组合后**必须重跑 `meta`**——拼接最容易把 summary 顶过 400 或把首句撑过 80 字。标题若被换成非原文，按第 2 条写理由。
5. **写下选择理由**：按下面的模板记进交付回复，别只丢一个结果。

**候选对比表模板**（「原标题」列填 是 / 否+理由）：

| 候选 | 角度 | 原标题 | 机检（title / summary / warnings） | 7 项不通过项 | 结论与理由 |
|---|---|---|---|---|---|
| A | 结论 | 是 | … / … / 0 | 无 | 备选：数字扎实，但读者未必先关心耗时；标题沿用 h1 原文 |
| B | 问题 | 是 | … / … / 0 | 无 | **定稿**：读者正是要跑发布的人，「白建页面」是他们真会踩的坑 |
| C | 方法 | 是 | … / … / 1 | #3 首句过长 | 淘汰：微信卡片停在半句 |

### 兜底：整批都不合格才换一批

绝大多数情况**一批就够，不必走满任何轮次**。只有整批候选全被淘汰时，才带着淘汰原因重新生成一批（换角度，别把上一批换个词再交一遍），**最多 3 批**。第 3 批仍全不合格，取问题最少的一版，明确标注「未通过编辑审查」并列出剩余问题，交给用户决定改字还是照发——不静默降级、不假装通过、不擅自发一个自己都判不合格的版本。

## 七、一个完整的三候选择优例子（原标题不适用分支）

样本：`CAPTURE_PIPELINE_GUIDE.html`（118KB、11 章、7 表、13 代码块、11 幅内联 SVG，两跳发布实测，见 `pipeline-facts.md`）。**这一批走的是「原标题未提供」分支**：实测底稿没有记录该文档的 h1 / `<title>`，无从沿用，因此按第二节「原标题不合格才自拟」处理——三版标题都自拟，对比表「原标题」列全为「否」，并须写明理由。同一份正文，一次写三版：

> 对照「原标题可用」的情况：仓库里 `research/free-web-hosting-2026.html` 的 h1 是 `免费部署 Web 应用的云服务全景研究`（19 字），第二节四条判据全过，应**直接定稿、标题不进候选池**；三组候选共用这个标题只比摘要，`shortlist` 传 `doc_title` 后 `recommended` 会优先原文标题版。本节演示的是另一种分支。

**A · 结论导向**

> 标题：`两跳发布管线：118KB 文档约 20 秒变成微信可分享卡片`
>
> 摘要：`实测一份 118KB、含 11 章与 11 幅内联 SVG 的 HTML，约 20 秒可走完资料库公开页与研究成果站两次登记，产出带专属封面的分享卡片。链路把 import_html.py 与 publish_page.py 拼成第 1 跳，再以 POST /api/items 完成第 2 跳，用 library:<node_id> 作幂等键支持重跑。验收不看返回码：health 条数从 58 到 59、详情页 200、封面图 5915 字节大于 2000、首页能找到条目标题，四项全对才算成，且新建返回 201 而非 200。标题与摘要按 UTF-16 码元在上传前校验 300 / 400 上限，避免第 2 跳被拒时第 1 跳已白建页面；文档型需剥掉 script 过 WAF，代价是原文不可改，只能删除重发。`

**B · 问题导向**

> 标题：`两跳发布不是事务：把白建资料库页面的字数校验挪到上传前`
>
> 摘要：`第 1 跳传完 HTML 页面就真建好了；第 2 跳才因摘要超 400 字被拒，那个页面就白留着。2026-11-03 实测踩过一次 403 字的摘要，资料库里因此多出一个用不上的页面。管线把字数校验前置到上传前，按 UTF-16 码元对齐服务端 JS s.length 的 300 / 400 上限，超限时资料库连页面都不会建。发布后按 health 条数、详情页 200、封面图大于 2000 字节、首页可找到标题四项验收，新建返回 201、幂等重投返回 200，用 library:<node_id> 保证重跑只更新不新增。链接型保留脚本交互但依赖两个域名；文档型全在站内、需剥掉 script 过 WAF，隔离由 CSP sandbox 承担，代价是原文不可改，只能删除重发。`

## 八、边界

- 这套标准管的是**卡片上的两个字段**，不管正文怎么写，也不替代 `precheck.py` 的 WAF / 体积体检。
- 字数、套话、格式可机检；**事实是否属实、结论是否从正文得出、读起来是否想点开**，脚本判不了，必须人工判。
- 目标区间是编辑要求、不是接口约束：确有理由越界（例如标题本身是个长专名）时，在候选对比表里写明理由即可，不必硬凑字数；**沿用文档原标题时 20–40 区间自动豁免**，300 字硬上限不豁免。
- 「优先原标题」不是「必须原标题」：原标题超 300 字、是文件名 / 占位符、带营销腔或格式杂质时判不可用，改写并在对比表写明理由；反过来，原标题合格却只因为「卡片句式更好看」而改写，判 #4 不通过。
- 候选数不是硬规定，角度分不开就别硬凑；**绝大多数情况一批就够**，只有整批不合格才换一批（最多 3 批），不必走满任何轮次。
- `shortlist` 的 `recommended` 只按形式排序，最终选择权在技术编辑；脚本推荐与人工选择不一致时以人工为准，并把理由写进候选对比表。
- 改了展示端截断值（`lib/render.js` 的 80 / 220），要同步改 `publish.py` 的 `OG_DESC_LIMIT` / `POSTER_SUMMARY_LIMIT` 与本文第一节。
